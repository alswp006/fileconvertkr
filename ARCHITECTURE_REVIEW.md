# Architecture Review
Generated: 2026-09-23T21:46:34.851Z
Score: 45/100

## Summary
The component/UI layer (src/components, src/pages) is unusually disciplined for an AI-scaffolded app — consistent SDK-guarding patterns, a real design-system wrapper layer (Amount, Card, PageShell), and thorough tests. However, the core data/orchestration layer is critically incomplete: runJob, buildJob, toHistoryEntry, deliverFile, finishJob, and useConversionRunner are all unimplemented stubs that throw, meaning the app cannot actually run a conversion end-to-end today. There is also a serious, unresolved split-brain between src/lib/contract.ts (an unused, auto-generated 'spec' type file with different ToolType values and field names) and the real src/lib/types.ts that the app actually uses, plus repeated copy-pasted haptic-feedback boilerplate across many components. No circular dependencies were found.

## Issues
### Critical
- [dead_code] The core conversion pipeline — running a job, saving it, delivering the output file, and finishing/navigating — is entirely unimplemented. Every one of these exported functions throws 'not yet implemented', so no tool (HEIC, compress, PDF merge/split/to-image) can complete a conversion despite the UI layer being fully built around them. — Files: src/lib/runJob.ts, src/lib/deliverFile.ts, src/lib/finishJob.ts, src/hooks/useConversionRunner.ts / Fix: Implement these functions per their documented contracts (runJob's per-file timeout/partial-failure semantics, deliverFile's saveBase64Data-then-anchor-fallback, finishJob's save→append→navigate sequence) before any tool page can be considered functional.
- [consistency] Two incompatible domain models coexist: contract.ts declares ToolType as 'heic-convert' | 'image-compress' | ... and a Job/ConversionResult shape keyed by `id`, while lib/types.ts (the one actually used everywhere) declares ToolType as 'heic' | 'compress' | ... and ConversionJob keyed by `jobId`. The mismatch has already leaked into runtime code — jobStore.ts has defensive fallback logic reading `job.jobId ?? (job as unknown as {id:string}).id` to paper over the divergence. — Files: src/lib/contract.ts, src/lib/types.ts, src/lib/jobStore.ts / Fix: Delete or clearly archive contract.ts now that implementation has diverged from it, and make lib/types.ts the single source of truth; remove the `id`/`jobId` fallback shim once nothing produces the legacy shape.

### Warnings
- [duplication] The 'fire a tick/success haptic, swallow throw outside WebView' snippet (`Promise.resolve(generateHapticFeedback({...})).catch(()=>{})` wrapped in try/catch) is copy-pasted nearly verbatim in at least seven files instead of being a single shared utility. — Files: src/components/BottomCTA.tsx, src/components/FilePickSection.tsx, src/components/MergeFileList.tsx, src/components/SelectedFileList.tsx, src/components/TargetSizeSelector.tsx, src/components/result/OutputRow.tsx, src/components/FloatingTabBar.tsx / Fix: Extract a single `src/lib/haptics.ts` exporting `fireHaptic(type)` and import it everywhere, matching the pattern already used for `lib/analytics.ts` as the single SDK entry point.
- [consistency] Home.tsx calls `generateHapticFeedback({ type: 'tickWeak' })` directly in a bare try/catch without the `Promise.resolve(...).catch(()=>{})` wrapping that every other call site uses — the codebase's own analytics.ts documentation explains this wrapping is required because the SDK can return a rejecting promise, not just throw synchronously. — Files: src/pages/Home.tsx / Fix: Route Home.tsx's haptic call through the same shared helper used elsewhere (see the duplication finding above) so the async-rejection guard isn't silently missing on this one call site.
- [dead_code] contract.ts is a large, entirely unused parallel type-declaration file (Job, ConversionResult, runJobFn, historyRepoFn, FilePickSectionFn, ResultSummaryFn, ROUTES, etc.) — nothing in src/ imports from it, and it has already drifted out of sync with the real implementation (see the ToolType mismatch above), making it actively misleading rather than a helpful reference. — Files: src/lib/contract.ts / Fix: Remove contract.ts from the shipped src/ tree (move it to docs/ or .ai-factory/ if it must be kept as historical scaffolding spec) so it can't be mistaken for a live type source.
- [structure] src/lib/storage.ts (a bare localStorage facade) and the src/lib/storage/ directory (historyRepo.ts, prefs.ts, storage.test.ts) share the same base name at the same nesting level, which is confusing to navigate and easy to misresolve — `@/lib/storage` imports the facade file, not an index of the directory's higher-level repos. — Files: src/lib/storage.ts, src/lib/storage/historyRepo.ts, src/lib/storage/prefs.ts / Fix: Rename the low-level facade (e.g. `src/lib/kvStorage.ts` or `src/lib/storage/raw.ts`) to disambiguate it from the higher-level storage/ modules that depend on it.

### Suggestions
- [dead_code] `formatCurrency` and `cn` in utils.ts don't appear to be used by any component or page in the codebase — only `formatNumber` and `formatBytes` are actually consumed. — Files: src/lib/utils.ts / Fix: Remove unused exports or confirm via a repo-wide usage search before keeping them; dead exports increase surface area with no benefit.
- [duplication] pdf/merge.ts exposes two overlapping entry points for the same operation: `mergePdfs` (internal, returns a discriminated-union result) and `mergePdfBlobs` (a thin contract-adapter that calls mergePdfs and throws on failure) — duplicate public surface for one piece of logic. — Files: src/lib/pdf/merge.ts / Fix: Keep a single canonical function and have callers choose between throwing/result-object styles via a shared small adapter pattern used consistently across pdf/split.ts and pdf/render.ts too.
- [structure] Ownership of 'execute a conversion job' is split unclearly between `src/hooks/useConversionRunner.ts` and `src/lib/runJob.ts`/`buildJob` — both are stubbed and both appear to orchestrate the same run-files-and-produce-a-job flow, with no clear boundary on which one pages should call. — Files: src/hooks/useConversionRunner.ts, src/lib/runJob.ts / Fix: Make useConversionRunner a thin React wrapper that calls runJob/buildJob internally, and document that pages should only ever call the hook, never runJob directly.
- [naming] contract.ts types use a `Fn` suffix convention (runJobFn, historyRepoFn, ResultSummaryFn, FilePickSectionFn) that doesn't match the plain PascalCase interface naming used throughout the real, implemented codebase (ConversionJob, HistoryEntry, ToolMetaEntry) — a naming-convention mismatch between the two competing type systems. — Files: src/lib/contract.ts, src/lib/types.ts / Fix: Once contract.ts is removed/archived (see dead_code finding), this inconsistency disappears; if any of it is kept, align naming with the types.ts convention.
